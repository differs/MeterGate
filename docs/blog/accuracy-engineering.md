# 计费系统的准确性工程：五个比性能更致命的缺口

> MeterGate 技术博客第二篇。上一篇讲了双轨记账和压测抓到的资金 bug；
> 这一篇讲"性能解决之后"的问题——五个单测和压测都测不出来、
> 只在真实生产场景下暴露的准确性缺口，以及我们怎么封住它们。
>
> （原文仓库：github.com/differs/MeterGate，Rust 版：github.com/differs/stargate）

---

## 一、为什么"性能没问题"之后，准确性才是生死线

我们花了大量篇幅证明吞吐（22K req/s、每核效率恒定、Rust 版 42K）。
但冷静下来想：**LLM 网关的 QPS 由上游生成速度决定（10-60 秒/请求），
22K 的转发能力在真实场景根本用不上**。真正会杀死平台的从来不是性能，
而是：

```
❌ 用户被多扣了 0.01 元 → 投诉 → 客服查不到 → 信任崩塌
❌ 供应商账单比我们统计多 2% → 毛利虚高 → 平台实际在亏钱
❌ 价格调整后老订单按新价结算 → 对账永远对不上
❌ 消费者重平衡导致同一笔请求结算两次 → 用户多付
```

这些问题的共同点：**单测测不出来、压测测不出来、只在"真实上游 +
价格变更 + 重平衡 + 用户申诉"的组合场景下暴露**。

## 二、缺口 1：价格快照缺失（在途请求被重新定价）

**现象**：请求 10:00 发出（$10/M），10:01 价格下调到 $8/M，10:05 结算
完成——按 $8 收费。

**为什么危险**：不是金额对错的问题（$8 也没错），而是**不可复现**——
用户看到的账单、我们的统计、供应商的计价，三个口径对不上，对账
永远无法收敛。

**修复**：价格在**请求开始**时冻结进计量事件：

```go
// 事件携带请求开始时的价格快照
type PricingSnapshot struct {
    InputPer1M  int64     `json:"input_per_1m"`
    OutputPer1M int64     `json:"output_per_1m"`
    EffectiveAt time.Time `json:"effective_at"`
}

// 结算永远用快照，绝不查当前价格表
p := priceFromEvent(ev) // ev.Pricing ?? PriceFor(ev.Model)
```

**验证**：单测证明"价格 $10→$8 变更后，在途请求仍按 $10 结算"。

## 三、缺口 2：真实上游 usage 语义被 mock 掩盖

mock 的 usage 永远是 `{prompt:1, completion:10}`。真实上游有五种
我们没处理的行为：

| 上游行为 | 我们的处理（修复前） |
|----------|---------------------|
| o1 系列 `reasoning_tokens`（不计费但占 context） | ❌ 未解析 |
| `prompt_tokens_details.cached_tokens`（缓存命中） | ❌ 按全价收 |
| 中断流不返回 usage（部分供应商） | ✅ 本地计量兜底 |
| 429 限流 | ✅ 不计费 |
| 按字符/秒计费的非 token 模型 | ❌ 只有 token 计价器 |

**修复**：`internal/upstreamsim`——一个**上游行为模拟器**，构造五种
真实响应形态，验证解析和计费规则。这是准确性验证的基础设施：
**mock 掩盖真实性，模拟器暴露真实性**。

## 四、缺口 3：供应商对账未实现（毛利不可信）

**现状**：内部对账（PG vs ClickHouse）验证过；**我方 vs 供应商账单**
只有文档。

**后果**：OpenAI 账单说 100M tokens，我们统计 98M——差 2% 是缓存？
重试？中断？**不知道**。毛利是虚的。

**修复**：`ProviderReconciler`——我方聚合 vs 供应商账单，万分之五容差，
账单源可插拔（真 API / mock）：

```go
diffs, _ := recon.Run(ctx, "2026-08-07")
// 20% 差异 → 自动标记 + 告警（metergate_recon_within_tolerance == 0）
```

## 五、缺口 4：明细追溯缺失（用户申诉不可查）

用户说"这笔钱不对"时，之前只能翻数据库。修复：`GET
/admin/billing/request?request_id=xxx` → ClickHouse 明细行（计量 +
价格 + 状态完整链路）。**资金系统必须能回答"每一分钱去哪了"。**

---

## 六、缺口 5：重平衡结算一致性（at-least-once 的魔鬼细节）

Kafka 消费组重平衡时，同一事件可能被两个消费者实例各处理一次。
我们的防线：PG `ON CONFLICT` + Redis settle 幂等 + 分片去重。

**但"设计了"不等于"验证了"**——故障注入测试：

```go
// 同一事件并发投递 5 次（模拟重平衡/提交失败）
for i := 0; i < 5; i++ { go settler.Handle(ctx, ev) }
// → 恰好 1 条订单，余额只扣一次 ✅

// 两个 Settler（消费者组成员）处理同一批 100 事件
// → 恰好 100 条订单 ✅
```

## 七、方法论总结（准确性工程的四个层次）

```
① 单元测试       —— 脚本边界（clawback、幂等）
② 端到端小量     —— 固定请求精确性
③ 高并发压测+审计 —— 21 万请求分毫不差（上一篇）
④ 故障注入/模拟器 —— 重平衡、重复投递、上游语义（这一篇）
```

**以及一条新原则**：

> **mock 是性能测试的朋友，是准确性测试的敌人。**
> 性能测试需要"快且确定"的 mock；准确性测试需要"真实且多变"的
> 模拟器——两者必须分开。

## 附：现在的准确性全景

```
✅ 双轨记账 + clawback          ✅ 幂等执行（created 标志）
✅ 零完成保险（失败免费）        ✅ 三层对账 + 自动补退
✅ 价格快照（在途不重定价）      ✅ 明细追溯（申诉可查）
✅ 供应商对账（毛利可信）        ✅ 故障注入（重复投递安全）
✅ 上游语义模拟器（真实差异可解释）
✅ 可观测性（7 条 SLO 告警：错误率/延迟/事件丢失/冻结泄漏/lag/对账）
```

**下一场仗**：把准确性从"验证过"推进到"商用完备"——支付链路、
用户体系、风控。那些没有性能问题，也没有新的准确性挑战，只有工作量。
