# 开源 LLM 网关的计费精度：从"总额度扣除"到"分毫不差"

> MeterGate 的技术博客第一篇。我们做了一个开源商用量级 AI 网关
> （github.com/differs/MeterGate），本文讲它最硬核的部分：**计费**。
> 核心数据：21 万请求压测下，订单、明细、余额三方分毫不差。

---

## 一、为什么计费精度是 LLM 网关的生死线

如果你用过任何"AI 中转站"，一定见过这类帖子：

> "XXX 站跑路了，余额还没用完"
> "这个中转站多扣了我 3 块钱"
> "流式回答中断了，钱照扣"

中转站的商业模式是"批发转零售"：从上游拿 Token 批发价，加价卖给用户。
**利润率 20-40%，但一次计费事故就能吃掉一个月的利润，两次事故就能杀死信任。**

而现有的开源方案（one-api / new-api / LiteLLM）在计费上有个共同的致命伤——
我们逐行读了它们的代码，并做了实测：

| 系统 | 额度扣减方式 | 实测吞吐（100 并发） | 对账 |
|------|-------------|---------------------|------|
| one-api (SQLite 默认) | **读-减-写，非原子**（并发下丢更新） | 58 req/s | 无 |
| one-api (PostgreSQL) | 非原子 | 495 req/s | 无 |
| new-api | 原子 SQL | 146 req/s | 部分 |
| LiteLLM | Redis 计数器 + DB 兜底 | 213 req/s | 无 |

**"非原子扣减"意味着什么？** 读余额 → 减额度 → 写回，三步之间如果有并发请求，
两个请求可能都读到同一个余额，各减各的——**用户实际被扣的比账单少，平台亏钱；
或者反过来，多扣了，用户跑路。** 这正是"跑路站"的常见死因：不是老板想跑，
是账对不上。

## 二、设计：双轨记账（Dual-Track Metering）

我们的方案借鉴了支付系统的成熟做法：**预授权 + 清算分离**。

```
请求到达
  │
  ├─▶ 快路径：Redis Lua 原子预扣（防超卖）
  │     balance:user 余额足够 → 原子扣减估算额 → 放行
  │     余额不足 → 402 拒绝（请求根本没碰到上游）
  │
  ├─▶ 热路径：流式转发 + 本地 token 计量
  │     每个 SSE chunk 增量累计（本地 tokenizer，独立于上游）
  │
  └─▶ 慢路径：异步结算（精确）
        事件 → 攒批（500 条/50ms）→ PG 终态订单（request_id 幂等）
        → Redis 结算脚本：多退少补
```

三个关键设计：

### 1. 钱永远用整数算

浮点数在金融领域是原罪：`0.1 + 0.2 != 0.3`。
全链路用 **int64 微元**（1e-6 基本货币单位），价格表、预扣、结算、对账全部整数运算，
**舍入是确定性的、可复现的**——这是对账能"分毫不差"的前提。

### 2. 幂等键贯穿全链路

每个请求由网关生成 `request_id`（UUID v7），作为贯穿始终的幂等键：

```sql
CREATE TABLE orders (
    request_id TEXT PRIMARY KEY,   -- 幂等防线
    ...
);
INSERT ... ON CONFLICT (request_id) DO NOTHING;
```

网络重试、Kafka 重放、对账重跑——**任何重复操作都不会产生第二条订单**。

### 3. 流式计量交叉校验

SSE 流式下 token 是"边吐边算"的。我们做了两层：
- **本地计量**：网关对每个 chunk 增量 tokenize（本地独立计量）
- **上游 usage**：流结束后上游返回的官方数字

两者交叉校验，差异 >1% 触发审计告警。计费以上游为准（与供应商结算口径一致），
本地计量用于**流中断兜底**（客户端断开时按已累计量计费）和**异常检测**。

## 三、压测抓到的 4 个真实 bug（最值钱的部分）

我们搭了全栈环境（PG + Redis + ClickHouse + Kafka + mock 上游）跑了 21 万请求，
**压测抓到了 4 个真实 bug，其中 2 个是资金漏洞**：

### 🔴 Bug 1：流式响应超扣预授权后，差额从未补扣

预扣额按 `prompt + max_tokens 封顶` 估算（约 237 微元）。但流式响应可能吐 300 个
token（3000 微元）——**结算时只释放预扣的 237，超出的 2763 微元从没从余额扣**。
用户少付了 92%。

```
修复前：pre=237, charged=3000 → 释放 237，超额 2763 永久丢失
修复后：pre=237, charged=3000 → 释放 237 + DECRBY balance 2763（clawback）
```

### 🔴 Bug 2：零完成保险仍收 prompt 费用

"失败请求不计费"是 OpenRouter 的公开承诺（zero-completion insurance）。
我们的实现里，failed 请求虽然标记为 NO_CHARGE，但**订单金额仍然包含 prompt
token 的费用**（每个失败请求约 25 微元，31,309 个失败请求 = 782,725 微元）。
**失败请求应该完全免费**——不只是 completion，prompt 也不收。

### 🟡 Bug 3：结算在事件处理线程同步执行

高并发下（>4K req/s），Settler 的批量写库在事件消费线程里同步执行，
导致事件堆积、缓冲溢出丢事件。改为**异步触发式单 flusher goroutine**。

### 🟡 Bug 4：非流式失败路径不产生事件

上游 5xx 时网关直接返回 502，**不 emit 计量事件**——失败请求对账不可见。
修复后失败也产生事件（审计 + NO_CHARGE 记录）。

**这些 bug 单测都测不出来**——它们只在"并发 × 流式 × 失败混合"的真实负载下
才暴露。这也是我们坚持写压测的原因：**计费系统不是"写对"的，是"审出来的"。**

## 四、结果：21 万请求，分毫不差

| 验证项 | 结果 |
|--------|------|
| 事件丢失 | **0**（缓冲溢出归零） |
| PG 订单 = ClickHouse 明细 | **完全一致**（213,600 条 / 48,414,690 微元，两边相等） |
| 余额（1e11 起始，预扣+结算+clawback） | **精确到微元** |
| 冻结余额（未结算预扣） | **0**（无泄漏） |

吞吐（完整计费链路开启，docker 全栈）：

| 场景 | MeterGate | one-api(PG) | litellm |
|------|-----------|-------------|---------|
| 100 并发非流式 | **5,511 req/s** | 495 | 213 |
| 流式 50 并发 | **323 req/s**（理论值 322，零瓶颈） | 181 | 101 |

> 开源项目的数据是**裸转发**；MeterGate 的数字**包含全部计费管线**。
> 差距的根源：我们把数据库移出了热路径（路由决策零 DB 调用、事件异步化、
> 批量提交），而开源项目每请求 3-5 次同步 DB 往返。

## 五、架构全景

```
client ──▶ Gateway (stateless, Go)
             │  fast path: Redis Lua pre-charge (atomic, no oversell)
             │  hot path:  stream + local token metering
             ▼
           metering events ──┬─▶ Kafka `metering.events` (event bus)
                             └─▶ ClickHouse `billing_detail` (audit, TTL 180d)
             ▼
           Settler (batch 500/50ms) ──▶ PostgreSQL orders (terminal state,
                                        idempotent) ──▶ reconcile CLI
```

- **路由引擎**：价格反平方加权（$1 vs $3 渠道 9:1 流量分配）、30 秒故障窗口、
  熔断器、fallback 链（4xx 永不重试）——对标 OpenRouter 的默认策略
- **对账引擎**：三层对账（订单完整性 / 冻结泄漏 / 日切）+ 自动补退
  （小额自动执行、大额人工审批、幂等防重跑）
- **LedgerAdapter**：资金存储边界接口（PG 默认实现，TigerBeetle 可插拔）
- **Auto Router**：`model:"auto"` 本地打分路由（<1ms，零外部调用）

## 六、给同行的建议

1. **钱用整数算，别用 float**——这是所有计费 bug 的地基
2. **预授权 + 清算分离**——防超卖和精确计费可以同时满足
3. **幂等键 + 唯一约束**——重试、重放、重跑永远安全
4. **异步化 + 批量提交**——计费不能阻塞请求热路径，但也不能每请求一次 fsync
5. **写压测，审账单**——21 万条真实订单审计出的 bug，比 100 个单元测试值钱
6. **零完成保险**——失败请求完全免费，这是信任的底线
