# 开源了个商用量级 AI 网关：5,511 req/s 下计费分毫不差（附 4 个真实资金 bug 复盘）

（V2EX / 掘金 / 知乎 发布版）

---

## 太长不看

做了个开源项目 **MeterGate**（github.com/differs/MeterGate）：商用量级 AI Token 聚合网关，对标 OpenRouter 的计费能力。核心成果：

- **21 万请求压测，订单、明细、余额三方分毫不差**（精确到微元）
- 100 并发 **5,511 req/s**（同条件 one-api 495、litellm 213——而且它们是裸转发，我们含完整计费链路）
- 压测抓到 **4 个真实 bug，其中 2 个是资金漏洞**（详见下文，这部分最值钱）

## 为什么做这个

现在做 AI 中转站的人很多，但开源方案（one-api / new-api / LiteLLM）在计费上有个共同的致命伤：**额度扣减是非原子的**（读-减-写三步，并发下丢更新），**没有对账**，**没有退款机制**。

我们逐行读了它们的代码并实测：

| 系统 | 扣减方式 | 100 并发吞吐 |
|------|---------|-------------|
| one-api (SQLite 默认) | 读-减-写非原子 | 58 req/s |
| one-api (PG) | 非原子 | 495 req/s |
| new-api | 原子 SQL | 146 req/s |
| litellm | Redis 计数器 | 213 req/s |

中转站毛利 20-40%，**一次计费事故吃掉一个月利润，两次事故杀死信任**。"跑路站"很多时候不是老板想跑，是账对不上。

## 核心设计：双轨记账

```
请求 ──▶ Redis Lua 原子预扣（防超卖，余额不足 402）
      ──▶ 流式转发 + 本地 token 计量
      ──▶ 异步结算：攒批 500 条/50ms → PG 终态订单（request_id 幂等）
           → Redis 结算脚本多退少补
```

三个关键决策：
1. **钱用 int64 微元整数算**——float 是金融原罪，整数运算的舍入是确定性的，这是"分毫不差"的地基
2. **幂等键贯穿全链路**（request_id + ON CONFLICT DO NOTHING）——重试/重放/重跑永远安全
3. **本地计量 vs 上游 usage 交叉校验**——>1% 差异触发审计；流中断按本地累计兜底

## 压测抓到的 4 个真实 bug（重点）

搭了全栈（PG+Redis+ClickHouse+Kafka+mock）跑 21 万请求，抓到：

**🔴 Bug 1：流式超扣预授权后差额从未补扣**
预扣按估算 237 微元，流式实际消费 3000 微元——结算只释放预扣的 237，**超出的 2763 永久丢失，用户少付 92%**。修复：结算脚本 clawback 补扣。

**🔴 Bug 2：零完成保险仍收 prompt 费用**
失败请求标记 NO_CHARGE 但订单金额还包含 prompt 费用（31,309 个失败请求 = 782,725 微元）。修复：**失败请求完全免费**（OpenRouter 的 zero-completion insurance 语义）。

**🟡 Bug 3：结算同步阻塞事件消费**——>4K req/s 时丢事件，改异步触发式 flusher。

**🟡 Bug 4：非流式失败路径不产生事件**——失败请求对账不可见，修复后 emit failed 事件。

> 这些 bug **单测都测不出来**，只在"并发 × 流式 × 失败混合"的真实负载下暴露。
> 计费系统不是写对的，是审出来的——21 万条真实订单审计比 100 个单测值钱。

## 顺手做的

- **路由引擎**：价格反平方加权（$1 vs $3 渠道 9:1 流量）、30s 故障窗口、熔断器、failover
- **三层对账 + 自动补退**：小额自动执行、大额人工审批、重跑幂等
- **Kafka 事件总线 + ClickHouse 明细层 + LedgerAdapter**（PG 默认，TigerBeetle 可插拔）
- **Auto Router**：`model:"auto"` 本地打分（<1ms）
- **docker compose 一键起全栈**，MIT 协议，纯 Go
