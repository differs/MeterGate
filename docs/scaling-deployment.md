# MeterGate 水平扩展部署方案

> 从"单机验证"到"生产水平扩展"的可落地指南。
> 验证依据：1/2/4 实例压测每核效率恒定（~6K req/s/核，Go 版），
> 计费完整性在多实例 + Kafka 消费者组下分毫不差。
>
> 原则：**每一步只加实例/分区/分片，架构拓扑不变**；每一步独立可逆。

---

## 1. 目标拓扑

```
                         ┌──────────────────────────────────────────────┐
    用户 ──▶ Anycast/NLB ──▶  K8s 集群（多可用区）                        │
                         │                                              │
                         │  ┌───────────┐  ┌───────────┐  ┌───────────┐ │
                         │  │ Gateway-1  │  │ Gateway-2  │  │ Gateway-N │ │
                         │  │ (无状态)   │  │ (无状态)   │  │ (无状态)   │ │
                         │  └─────┬─────┘  └─────┬─────┘  └─────┬─────┘ │
                         │        │              │              │       │
                         │        │ Redis 集群（预扣/余额，分片）          │
                         │        │              │              │       │
                         │        └── Kafka metering.events ────┘       │
                         │              （分区 = 消费者成员数 × 2+）       │
                         │                    │                         │
                         │        ┌───────────┴───────────┐             │
                         │        │ Settler 消费者组        │            │
                         │        │ （每网关实例 1 成员，    │            │
                         │        │  自动重平衡）           │            │
                         │        └───────────┬───────────┘             │
                         │        PG 主 + 备 + 只读副本                  │
                         │        （分库：hash(user_id) % N，零跨库事务）  │
                         │        ClickHouse 明细（多副本）               │
                         └──────────────────────────────────────────────┘
```

**关键设计**（全部经过验证）：
- 网关无状态：热路径零 DB（路由快照内存、预扣 Redis、事件异步）
- Kafka 消费者组：N 实例 = N 成员自动负载均衡（分区重平衡时 PG ON CONFLICT 幂等兜底）
- 事件生产 Async：网关永不阻塞
- 分库零跨库事务：事务边界天然在单用户内

## 2. 各组件扩展配置

### 2.1 网关（数据面）

| 项 | 配置 |
|----|------|
| 部署 | K8s Deployment，副本 = 按需（HPA） |
| 资源 | 每副本 2-4 核 / 2-4 GiB（每核 ~6K req/s） |
| HPA 指标 | CPU 利用率 70% + 自定义指标（活跃连接数） |
| 优雅排空 | preStop sleep 10s + terminationGracePeriodSeconds 120（存量 SSE 流完成） |
| 就绪探针 | `/healthz`（200 即就绪） |
| 存活探针 | `/healthz` |
| 每实例能力 | 100 并发 22K req/s；每核 ~6K（Go）；Rust 版 1.3x |

**容量换算表**（目标 10 万 req/s 建立速率）：

| 实例数 | 每实例并发 | 总吞吐 | 备注 |
|--------|-----------|--------|------|
| 1 | 100 | 22K | 起步 |
| 4 | 100 | ~88K | HPA 自动扩 |
| 8 | 100 | ~176K | 单地域上限参考 |

### 2.2 入口（LB）

| 参数 | 值 | 原因 |
|------|-----|------|
| idle timeout | **关闭或 ≥ 10min** | SSE 长连接不能被切断（默认 60s 会杀流！） |
| proxy protocol | 开启（若需真实客户端 IP） | 风控/审计 |
| 连接数 | NLB 单节点百万级 | 不是瓶颈 |
| TLS | 终结于 LB | 网关纯 HTTP |

### 2.3 Kafka / Redpanda（事件总线）

```
分区数 = 消费者成员数 × 2（留重平衡余量）
建议：
  4 网关实例 → 8-12 分区
  16 网关实例 → 24-32 分区
  64 网关实例 → 64-96 分区
```

| 参数 | 值 |
|------|-----|
| topic | `metering.events`（分区键 = request_id 哈希，保序） |
| 消费者组 | `metergate-settle`（所有实例同组，自动重平衡） |
| 消费者批量 | 500 条 / 200ms，一次 CommitMessages（85K events/s 实测） |
| 生产者 | Async + BatchSize 500 / 50ms（网关零阻塞） |
| 保留期 | 7 天（重放窗口） |

### 2.4 PostgreSQL（账务）

```
阶段 1（单库）：主 + 同步备（RPO=0）+ 只读副本 ×2
阶段 2（分库）：hash(user_id) % N，N = 4/8/16
```

| 分库数 | 每库写 TPS（10万 req/s 场景） | 对账 |
|--------|------------------------------|------|
| 1 | ~10K TPS（攒批后 OK） | 单库跑批 |
| 4 | ~2.5K TPS | 4 并行，结果合并 |
| 8 | ~1.2K TPS | 8 并行 |

**分库实施**（双写迁移，可回滚）：
```
① 双写：新分片开启写入（旧库继续）
② 回填：历史订单按 shard_id 导入
③ 校验：行数 + checksum 100% 一致
④ 切读：1% → 10% → 50% → 100% 灰度
⑤ 切写：旧库转只读，保留 90 天回滚窗口
```

### 2.5 Redis（热状态）

| 项 | 配置 |
|----|------|
| 模式 | 集群（>=6 节点：3 主 3 从），16384 槽 |
| 数据 | balance/frozen/precharge（TTL 48h）+ 限流窗口 |
| 容量 | 45 万并发场景峰值 ~10GB（预扣记录）→ 集群 64-128GB |
| 降级 | 不可用时"宽进严出"（见降级策略） |

### 2.6 ClickHouse（明细）

```
多副本（ReplicatedMergeTree），4 节点起步
写入：3.2 亿行/天 → 4 节点富余 30 倍
查询：用户明细/追溯 API 走这里（PG 不扛查询）
```

## 3. 分步扩容操作指南

### 阶段 1 → 阶段 2（1 实例 → 4 实例，约 30 分钟）

```
1. Kafka：topic 分区 3 → 12（rpk topic alter / kafka-topics）
2. 网关：Deployment replicas 1 → 4（HPA 自动或手动）
3. 验证：
   - kubectl get pods：4/4 Ready
   - 消费者组：MEMBERS = 4（rpk group describe metergate-settle）
   - 压测：总吞吐应 ≈ 4 × 单实例（每核效率恒定）
   - 计费：压测后 PG = CH（Layer A 一致）+ 余额精确 + frozen 0
4. 监控：
   - metergate_kafka_consumer_lag 应回落 0
   - metergate_sink_dropped_total 应保持 0
   - metergate_frozen_balance_micros 应 ~0
```

### 阶段 2 → 阶段 3（4 → 16 实例 + 分库）

```
1. Kafka：分区 12 → 32
2. PG 分库：hash(user_id) % 4（按第 2.4 节迁移五步）
3. 网关：replicas → 16
4. 验证：同阶段 2 + 分库后对账并行（4 库跑批结果合并一致）
```

### 阶段 3 → 阶段 4（多地域）

```
1. 每地域独立：网关 + Kafka 分区 + CH（PG 主地域 + 跨地域只读）
2. 路由：DNS/Anycast 就近接入（TTFB 优化）
3. 账务：单主地域写，跨地域只读副本（对账 T+1 从副本跑）
```

## 4. 扩展下的运维要点

| 场景 | 要点 |
|------|------|
| 滚动发布 | preStop drain（存量 SSE 最多等 2min）+ 客户端 SDK 自动重试 |
| 缩容 | 先摘流量（Ingress 排空）再缩副本，避免消费者组抖动 |
| Kafka 重平衡 | 预期内（幂等兜底）；观察 lag 短暂上升后回落 |
| 分库故障 | 单分片降级只读 + 告警，其余分片无感 |
| 大客户 | 独立分片（dedicated shard）隔离热点 |
| 容量规划 | 每核 6K req/s（Go）/ 8K（Rust）；连接数 ≈ 活跃用户数 |

## 5. 验证清单（每次扩容后必查）

```
□ 网关 pods Ready = 目标数
□ 消费者组 MEMBERS = 网关数（自动重平衡）
□ Kafka lag 压测后 = 0
□ Layer A：PG orders == ClickHouse details（count + amount）
□ 余额精确（1e11 - Σamount - frozen == balance）
□ frozen = 0（无预扣泄漏）
□ metergate_sink_dropped_total = 0（事件零丢失）
□ 5xx 比例 < 0.1%（SLO 99.9%）
□ 每核效率 ~6K req/s（相对指标，不受环境负载影响）
```

## 6. 配置速查（环境变量）

| 变量 | 多实例注意 |
|------|-----------|
| `METERGATE_PORT` | 容器内固定 3000（Service 路由） |
| `METERGATE_KAFKA` | 所有实例指向同一 Kafka 集群（同 topic 同 group） |
| `METERGATE_PG_DSN` | 同库（阶段 1-2）；分库后按 shard 配置 |
| `METERGATE_REDIS_ADDR` | 同一 Redis 集群（所有实例共享余额） |
| `METERGATE_CLICKHOUSE` | 同一 CH 集群 |
| `METERGATE_API_KEYS` | 同一组（或接入 Key 服务） |
